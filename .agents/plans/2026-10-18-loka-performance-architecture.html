Browser: what the C++ service owns
  • LokaSpacesService, one per profile, as in the v1 plan. It keys tabs by TabHandle and holds lookups as hash maps, so finding a tab's space is O(1). Today that lookup is Object.entries(...).find in a loop.
  • One observer per window feeds the service. Today the sidebar, the hidden command bar, settings and the empty tab each watch the tab strip and build their own tab list.
  • It saves with ImportantFileWriter, which batches writes and writes off the UI thread. A title change marks the file dirty; it doesn't write.
  • Last-used times stay in memory and are saved with the batch, not on every activation.
  • The archive lives in its own file, read only when the Library or archive panel opens. It never travels with the sidebar's state.
Messages: what crosses, and how often
  • A loka_sidebar.mojom interface. The page sends intents (ActivateSpace, ActivateTab, MoveItem). The service answers with one OnChanged holding just the changed fields: {tab 812: title}, not the tab list.
  • C++ collects changes and sends at most one batch per 16 ms. Loading spinners and titles during a page load collapse into that batch.
  • Icons travel as a URL, chrome://favicon2/… for saved pages or a small Loka icon source keyed by tab and version. The bytes never go through a message, and the browser's image cache dedupes them. Today each icon is a base64 PNG resent in every snapshot.
  • Only the sidebar subscribes to tab changes. The command bar asks once when it opens.
  • The page loads with one GetInitialState call, then only changes. Other spaces' rows arrive too: 300 rows of id, title, URL and icon URL is roughly 60 KB (an estimate). That's what lets a switch skip the round trip.
  • The 60-second archive timer moves into C++ as one timer for the next due tab, and does nothing when archiving is off.
Sidebar page: how a switch fits in one frame
  • Paint first. The page already has every space's rows, so a click swaps the list right away and sends the intent. If C++ refuses, the list goes back and nothing is lost.
  • Keep recent lists built. The current space and the two neighbours stay in the DOM, with content-visibility: hidden on the ones you can't see. Showing one skips building 150 rows, which is most of today's 108 ms long task.
  • Stable rows. Each change replaces only the changed row objects, so Lit's keyed repeat updates just those rows. Today a new live object on every snapshot redraws the whole template.
  • Measure only when rows move. FLIP measuring runs only for moves the user made (a drag, a reorder). Today it reads every row's rect before and after each state change.
  • Rows keep content-visibility: auto. Virtualizing isn't needed below about 500 rows. The Library page is the exception: history can run to thousands, so it renders only what's on screen.
  • Sounds and the audio context start on first use after idle, never inside a switch. They once blocked a switch for 340–370 ms.
Motion: keeping the orbit and the stars cheap
  • The orbit, the sky fade, the star sweep and the list slide are WAAPI animations on transform and opacity only. That's how the mockup does it. Once they start, the compositor runs them with no main-thread work.
  • Planets are drawn once and scaled. Chrome rasters an animating layer at the largest scale in its keyframes, so the big planet stays sharp without redrawing each frame (inferred from how Chromium's compositor works; check in a trace).
  • No filter, backdrop-filter or drop shadows on anything that moves. The glow is a radial gradient, as in the mockup, where a drop shadow cost about 5 fps.
  • will-change goes on only for the switch and comes off after, so idle GPU memory stays low.
  • Stars cover only the sidebar, as in the mockup, where covering the whole window took idle from 60 to 38 fps.
  • Settings › Appearance › Moving stars: While I'm using Loka (default) drifts and stops 15 s after the last input; Always never stops while the window shows; Off keeps them still. Drifting stars keep the compositor drawing at 60 Hz; the stepped drift on record measured ~7% GPU.
  • The cheap path, for both moving modes: each depth is one pre-drawn layer, moved by transform only, covering the sidebar only. Nothing repaints; the GPU only re-composites three small textures each frame.
  • Every mode stops when the window is minimised, hidden behind others, or Energy Saver is on, and with reduced motion.
  • Always gets its own budget, set from what verify:perf measures. Worth trying in C++: asking the compositor to draw the sidebar at 30 Hz while only the stars move (inferred possible; not checked).
  • With reduced motion on, a switch is a 200 ms crossfade.
Memory and startup: what sleeps
  • Other spaces' tabs stay in the tab strip in collapsed groups, as today; that keeps Chromium's session restore working.
  • Three layers decide when a tab sleeps.
    1. Memory pressure, any background tab: Chromium's Memory Saver, as Arc used.
    2. A space no window shows: its tabs unload after 30 min unseen. Settings: 15 min, 30 min, 1 h, 2 h, Never.
    3. 12 h unused: open tabs go to the archive (the v1 plan).
  • Why a timer as well as pressure: Zen tried both. Its timed unloader (5–20 min, by version) drew "unloading too quickly" complaints. It moved to Firefox's pressure-only unloader in 1.12.9b, and now has reports that tabs never unload on macOS. 30 min sits between those.
  • Unloading uses Chromium's discard, so a tab keeps its Back history, title and icon, and reloads when you open it. Chromium's own rules skip tabs playing sound, using the camera, mic or screen share, holding unsaved form input, or downloading.
  • Unloaded pinned tabs and Essentials are rows with no WebContents, plus their saved history (v1 plan).
  • At startup only the tab each window shows is loaded. Other restored tabs wait until you open them.
  • The sidebar's first paint comes from GetInitialState during page load, so there's no empty frame of sky.
Right-click menus: why a floating window

A menu drawn inside the sidebar page can't leave the sidebar's 280 px, so submenus and menus near the edge get cut off. The command bar already uses a top-level popup page that stays warm after first use. Menus can share that host: it opens with no process start and draws your design. Native Windows menus open fastest but can't show the planet colours or Loka's type.

Where today's numbers come from, and what I didn't check
  • Today's column: bun run verify:perf -- --heavy --webui=checkout on 18 Oct, median of 3 runs on the 15 Oct dev build (a component build, so memory reads high), this branch's sidebar code. Byte sizes are one more run with --bytes.
  • Other programs used 22–47% of the 16 cores during those runs, so CPU and timing numbers are noisy. The message counts don't depend on load.
  • Per switch: 8.6 sent (getTabs and getGroups ×1.7 each, updateGroup ×1.6, setStore ×1.2, …). Per click: 6.2 sent, 8.1 back. Churn: 1,200 sent and 1,458 back in 20 s; the hidden command bar used 12.5% of a core on it.
  • Click to paint was 64 ms; key-to-paint for a switch was 200 ms, with long tasks up to 108 ms.
  • Budgets: scripts/verify-perf.mjs:49-77.
  • Snapshots and icons: the handler's TabList() and ScheduleTabsChanged in patches/loka/loka-native-sidebar.patch. Every tab-strip change in a task sends the full list plus media, with no time debounce.
  • Whole state per event: webui/src/store.ts:42-63 and sync.ts:47-58, 146-177.
  • Row measuring: loka-sidebar.ts:894-1011.
  • The 60 KB initial-state size and "one frame or two" for the C++ confirm are estimates, measured once the C++ side exists.
  • Orbit fps (50–60) is from the mockup in a normal browser tab, not the sidebar WebView.
  • Zen's unloader history: "unloading tabs too quickly", where the timer went, tabs never unload on macOS. Firefox's unloader waits at least 10 min idle (bug 1729911). Read 18 Oct 2026.
Risks
  • Paint first, refused after. If C++ refuses often, the list flickers back. It refuses only when the space was deleted in another window, which should be rare; --heavy should count refusals once they exist.
  • Kept lists cost memory. Three built lists of 150 rows is about 13,500 nodes, over today's 10,000 budget. Raise the budget for this or keep only one neighbour built.
  • Discarding breaks media or forms. Chromium already skips audible tabs and tabs with unsaved form input; Loka uses its rules, not its own.
