Auto-update: an installer, two keys, a Depot runner

Helium's WinSparkle updater is already in the tree, but it only runs for an installed browser, so the portable zip can never update itself. Loka needs an installer built by a CI workflow, an EdDSA key pair, a feed file on GitHub and one small patch.

Your call on five things

  1. Runner: depot-windows-2025-32 ($7.68/h, 200 GB disk) is the default. Prefer the 64-core or a self-hosted box?
  2. Versions: tag v0.19.2.N and bump revision.txt per release, dropping v0.1.0-alpha.N. The browser only compares the four-part form.
  3. Install identity: company and product Loka, new GUIDs. The default profile then moves to %LOCALAPPDATA%\Loka\Loka\User Data. Copy alpha users' profile on first run, or tell them to move it?
  4. Signing: ship unsigned with EdDSA now (per-user updates work), then Azure Artifact Signing ($9.99/mo) if you're in the US or Canada, else SignPath.
  5. Feed: an updates branch served from raw.githubusercontent.com, written when a release is published.

Done when

  • A clean Windows VM installs Loka-0.19.2.N-windows-x64-installer.exe and chrome://settings/help says it checked for updates.
  • After N+1 is published and the feed pushed, that VM offers "Relaunch to update" within an hour and runs N+1 with the profile intact.
  • bun run verify passes with LOKA_CHROME at the release build.

Order of work

  1. agent loka-install-paths.patch: install names, GUIDs, WinSparkle app details, kUpdateBaseUrl; installer/loka.nsi.
  2. you node scripts/alpha/appcast.mjs generate-key once. Secret LOKA_EDDSA_PRIVATE_KEY; variables WINSPARKLE_ED_KEY and WINSPARKLE_AUTHENTICODE_ORG. Back the seed up offline.
  3. you Connect the repo to Depot, or register a self-hosted Windows runner. Bump revision.txt.
  4. you, then agent Run loka-release.yml once. It measures the real build time and shows what breaks in an official build of Loka's patches.
  5. you Install the draft's installer on a VM, then publish the draft.
  6. agent loka-feed.yml (on release published, push appcast.xml to updates), a verify-loka feature for updates, docs.
  7. you When a signing account exists, add the six AZURE_* secrets; the workflow signs on its own.

Helium's stages run on 4 vCPU and lose time zipping and restoring build\src between jobs. Compiling scales close to linearly with cores, the final ThinLTO link does not, so 32 cores is not 8× faster.

Depot's docs list no persistent disk for Windows runners, so each run unpacks Chromium again. A self-hosted runner keeps the tree, but build.py --ci only resumes a tree as it is; applying a new Loka commit to an existing tree is what browser:setup plus loka_build.py incremental do on the laptop, and CI would need the same.

Disk: the dev tree is about 100 GB. An official build needs the source, a release out\Default and signing.py's staging copy; 200 GB should fit, 250 GB is safer. Unverified until the first run.

What the code checks, and where:

  • build.py lines 393 to 398: the updater is compiled in only when both WINSPARKLE_ED_KEY and WINSPARKLE_AUTHENTICODE_ORG are set. An unsigned build still needs a non-empty org string; only the all-users helper compares it.
  • third_party/winsparkle/src/signatureverifier.cpp: every download is checked against the 32-byte public key, a 64-byte Ed25519 signature over the whole file. No Authenticode check on this path.
  • helper.patch, payload_verifier.cc: the all-users helper requires WinVerifyTrust to pass, then either a matching O= or a valid EdDSA signature.
  • glue.patch, OnRunInstaller: per-user runs the downloaded mini installer with --do-not-launch-chrome; the swap (new_chrome.exe) happens at relaunch.
  • signing.py: Azure Artifact Signing through Microsoft.ArtifactSigning.Client 1.0.128 and signtool with a timestamp, then verifies every binary. Its six environment variables are the workflow's secrets.

Sources: Artifact Signing quickstart (updated 8 Oct 2026), its pricing, SignPath Foundation terms.

Rollback is roll-forward: pull the feed item, publish a higher number

WinSparkle only offers a version higher than the running one, and setup.exe refuses a lower one (exit 4, "higher version exists"). To pull a bad release, remove its item from win/appcast.xml so nobody else gets it, then publish the last good commit under a higher revision.txt.

Users who already have the bad build get the fixed one within the hour.

scripts/loka_release_build.py
Helium's build.py with Loka's two steps (build webui/, apply the brand and name) hooked in before gn gen, as loka_build.py does for dev builds. Imports and hooks; never run against a real build.
scripts/alpha/appcast.mjs and its test
Key generation, signing and the appcast XML, compatible with winsparkle-tool's key file. Five tests pass: a 32-byte public key, a 64-byte signature that verifies and fails when tampered, the enclosure attributes, alpha labels refused.

Scope: Windows x64 per-user installs; no macOS, deltas or channels

In: Windows x64, per-user install, hourly checks, a GitHub-hosted feed, draft releases from CI, optional Authenticode.

Out: macOS (Sparkle and notarization, see docs/cross-platform.md), delta updates, beta and stable channels, keeping a build tree between CI runs, all-users install updates without a certificate, the legacy extension.

Risks: six ways this fails, each with its answer
  • Loka's patches have never been built with is_official_build, and loka_brand.py apply has never run after Helium's own name substitution. The first CI run is a test run; budget a day of fixes.
  • The runner image lacks VS 2026, the SDK or 7-Zip. The toolchain step fails in the first minute, before any cost.
  • Disk runs out during packaging. Use the 64-core label (250 GB) or lower symbol_level in a Loka GN flag.
  • Alpha.12 users on the zip never hear about the installer. The release notes and the next zip's README say so; the zip stays for people who want portable.
  • The profile path change loses spaces. Decide question 3 before the first installer goes out.
  • The EdDSA seed leaks or is lost. Leak: ship a build with the new public key through the old key, then switch the feed. Loss: every installed copy is stuck until reinstalled. Back it up offline.
