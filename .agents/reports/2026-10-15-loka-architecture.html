Loka should drive real Chromium tabs

Every page stays a normal Chromium tab, and a C++ model decides which space it belongs to. Loka has the Helium base and the model's rules; the browser half hasn't started.

Three choices for you. Answer by number.

  1. Windows. Does each window show its own space (like Zen), or can two windows show the same space (like Arc)?
  2. Unloaded pinned tabs. Should they be Loka entries that extensions can't see? Or discarded Chromium tabs that keep their ID and back history but cost a slot in the tab strip?
  3. Order of work. Should we fix the two model bugs and add live-tab state in TypeScript before the first browser patch? I'd say yes.

A browser is many processes

Chromium runs one browser process, which owns windows, tabs and profiles. Each site's pages run in their own sandboxed renderer process.

The browser's own UI is C++, drawn with a toolkit called Views. Some UI is WebUI instead: a chrome:// page that runs in a renderer and asks the browser process for things.

Profile
One user's data: history, cookies, extensions. Per-profile C++ services are called KeyedServices.
Window
A Browser object, with BrowserView laying out its UI.
TabStripModel
A window's ordered list of tabs. Extensions, session restore and Ctrl+Tab all read it.
WebContents
One live page. A tab holds one while it's loaded.
WebUI
A trusted chrome:// page used as browser UI. Chrome builds tab search and its side panel pages this way.
Mojo
Chromium's typed messages between processes. This is how a WebUI page calls C++.

Patches are diffs replayed in order

Helium doesn't keep a copy of Chromium. Its build downloads Chromium's source, applies a list of patches in order (the series file), then compiles.

A patch says: in this file, next to these lines, remove these and add those. If Chromium has rewritten those lines, the patch fails and someone fixes it by hand.

Chromium ships a new stable version about every 4 weeks. So every line a patch touches becomes a chore to redo each month.

Check yourself: which patch survives a Chromium update?

Chromium moves 40 lines around inside browser_view.cc. Will a 2-line hook still apply? Will a 400-line patch to the same file?

The hook almost always applies. The patch tool finds the 3 unchanged lines around it at a new offset. The big patch has dozens of places that each need their surrounding lines unchanged, so one of them usually breaks. A brand new file never conflicts, because Chromium never touches it.

Small hooks keep merges cheap

So put the feature in new files, and have the patch to Chromium's file add only the call. Helium works this way: its components/helium_services/ folder arrives as new files inside its patches.

Two flows through the pieces

The diagram at the top, in motion. The second flow is the one the prototype can't do yet.

You click an unloaded pinned tab

  1. The sidebar sends “activate entry 42” over Mojo.
  2. The window controller checks entry 42 is in the active space.
  3. The entry has no live tab, so the controller opens one in the TabStripModel, at the index its ordering rule gives.
  4. It links entry 42 to the new tab and activates it.
  5. The page loads in its own renderer. The sidebar marks the row as live.

A link opens a new tab

  1. A page calls window.open, or an extension calls chrome.tabs.create.
  2. Chromium adds a tab to the TabStripModel without asking Loka.
  3. The controller sees “tab inserted” and adopts it: into the space of the tab that opened it, else the active space's open list.
  4. The service saves the change and the sidebar shows a new row.
  5. After a restart, session restore brings the tab back with its Loka ID, in the same place.

The two model bugs

  • activateTab() only checks that the tab exists. A tab from another space can become the active tab of the current one.
  • moveItem() never updates activeTabId. Drag the active tab to another space, and the old space still points at it.

Astra's review changed four things

GPT-6-Astra read the repo and my first proposal, and agreed with the direction. It corrected these four points, and I agree with all of them.

  1. Tab order matters. Extensions read and change tabs.index, and Ctrl+Tab follows it. Loka needs a fixed rule for flattening the sidebar tree into that order.
  2. An unloaded entry isn't a Chromium tab. That's why choice 2 above exists.
  3. Match by ID, never by URL. Store a Loka ID in Chromium's session data. Plan for Loka's file and Chromium's session log disagreeing after a crash.
  4. “Only hooks” is a goal. Tab activation, closing, restore and drag and drop will need real edits inside Chromium. Keep those edits few and small.

Astra also suggested two things to check first: Chromium's own vertical tabs code, and the startup and memory cost of a preloaded WebUI sidebar.

Build it in this order

  1. Helium builds unchanged, locally and in CI. The scripts exist; I didn't check whether a build has run.
  2. Fix the TypeScript model: the two bugs, live and unloaded state, an adoptTab entry point, and the window decision. These are cheap to test here.
  3. First patch: hide the tab strip and dock an empty WebUI sidebar. Measure startup and memory.
  4. C++ service, window controller and Mojo. The sidebar lists real tabs.
  5. Saving with Loka IDs. Test restart, crash, outside tabs and two windows together.
  6. Spaces, lazy pinned tabs, essentials, then colour, Ctrl+K, drag and drop, Loka's update feed and signing.
Check yourself: 2 questions on the design

An extension calls chrome.tabs.query({}). Does it see tabs from hidden spaces? Yes. Every live tab is in the one TabStripModel, whatever its space. Unloaded pinned entries show up only if choice 2 makes them discarded tabs.

You open the same URL twice in one space, then restart. How does Loka tell the two tabs apart? By the Loka ID stored with each tab in session data. Matching by URL would mix them up.
